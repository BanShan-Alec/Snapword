# Snapword 规格说明书：自定义翻译角色（Personas）

> **文档状态**：已定稿（已通过 `/brainstorming` 与用户对齐并确认）  
> **适用范围**：三窗口划词翻译体系中的主窗口「设置」与「翻译卡片」  
> **上游依据**：`docs/specs/PRD.md`（FR-11/12/17~23）、`docs/specs/interaction-spec-v2.md`（RC-01~20、RM-01~20）、`docs/contracts/prompt-contract.md`、`docs/contracts/data-model.md`  
> **领域词汇**：严格遵循 [GLOSSARY.md](../../GLOSSARY.md)（划词、取词、翻译卡片、主窗口、单词模式、句子模式、语境、语境义、会话历史等）

---

## Problem Statement / 问题陈述

在阅读英文技术文档或跨专业资料时，用户面临两个核心痛点：

1. **“无语境”导致盲猜与泛化**：受限于 Windows 特殊控件、跨域 iframe 或用户选中孤立词汇，取词服务有时无法通过 UIA 提取到包含该词的原句（即“无语境”降级）。此时模型缺失句内上下文锚点，只能像传统通用词典一样返回宽泛、脱离技术实际的常见义项。
2. **专业多义词理解偏差**：即使成功提取到上下文句子，计算机不同分支（如前端、系统底层、AI算法）以及其他专业学科（如金融、生物医学）的技术多义词（如 `state`、`pipeline`、`mount`、`yield`）存在强烈的行业偏向。单一写死的通用技术提示词无法精准对齐特定读者的专业背景，导致首项语境义偏离实际工作场景。

---

## Solution / 解决方案

以**轻量灵活、不打断日常阅读心流**为核心原则，构建「主窗口集中配置，卡片现场快捷切换」的翻译角色（Personas）体系：

1. **主窗口集中管理（CRUD）**：在主窗口「设置」页提供「翻译角色管理」模块，允许用户自定义新增、编辑、删除特定专业领域的角色（包含名称与 Prompt 人设描述），并可指定全局「默认角色」。系统内置一条不可删除的「通用技术」保底角色。
2. **卡片现场轻量切换（方案 B 自适应交互）**：翻译卡片头部自适应展示角色切换器。日常划词默认以设定的「默认角色」发起翻译；当用户发现释义不合意时，可现场点击切换角色，立即按新角色重新翻译。
3. **会话级请求与缓存**：在卡片当前展开的生命周期内，内存缓存各角色的请求结果（`Map<personaId, Result>`），切回已查角色 0ms 秒开且 0 token 消耗；卡片关闭时，仅将最终保留的结果存入 20 条会话历史。
4. **提示词契约无感替换与无语境增强**：保持底层 `word-v1` 严格 JSON 契约不变，仅将系统提示词首句动态替换为当前角色的专业描述；在无语境时，提示词注入该角色的先验领域偏好，卡片首项义项明确提示「未获取原句，已按【当前角色】推断」。

## User Stories / 用户故事

1. 作为技术读者，我希望在设置页中看到预置的「通用技术」角色，以便开箱即用无需任何额外配置。
2. 作为技术读者，我希望在设置页中添加自定义角色（如「前端工程师」），以便在查词时能注入我专属的专业技术背景。
3. 作为技术读者，我希望为自定义角色填写一小段 Prompt 背景描述（如「精通 React、TypeScript 与 Web 标准」），以便引导模型优先理解该领域的专用术语。
4. 作为技术读者，我希望对自定义角色进行编辑和重命名，以便随时修正角色的领域描述。
5. 作为技术读者，我希望删除不再需要的自定义角色，以便保持角色列表简洁清爽。
6. 作为技术读者，我希望系统保护出厂内置的「通用技术」角色不可被删除，以便即使我删除了所有自定义角色，系统依然有可靠的保底基线。
7. 作为技术读者，我希望在设置页中将某个角色标记为「默认」，以便每次划词弹出的翻译卡片都统一按该角色发起初始翻译。
8. 作为技术读者，我希望在 Chrome 中划词查词时，翻译卡片自动以默认角色发起翻译，以便我的日常阅读心流完全不被额外的选择动作打断。
9. 作为技术读者，当我的角色配置不超过 3 个时，我希望在翻译卡片顶部看到平铺的角色胶囊标签，以便在发现词义不合意时一键直切。
10. 作为技术读者，当我的角色配置超过 3 个时，我希望卡片顶部展示常用标签和一个「更多 ▾」下拉菜单，以便在卡片有限的 420px 宽度内不发生布局拥挤。
11. 作为技术读者，我希望在卡片中点击另一个角色标签时立即发起重新翻译，以便快速获取该词在另一个专业领域下的释义。
12. 作为技术读者，我希望卡片内切换回刚才已经查过的角色时能瞬间恢复已有的结果，以便不必重复等待网络请求也不浪费我的 API token。
13. 作为技术读者，我希望在卡片内切换多次角色后关闭卡片时，只有我最终停留在卡片上的结果被存入会话历史，以便 20 条会话历史不被单次查词的试错记录污染。
14. 作为技术读者，当 UIA 无法获取到上下文原句时，我希望卡片首项释义明确标注「未获取原句，已按【当前角色】推断」，以便我清晰了解当前释义是基于领域推测而非具体原句。
15. 作为技术读者，当 UIA 无法获取到上下文原句且我切换了角色时，我希望卡片首项的推断标签同步更新为新角色名，以便我准确获知当前结果基于哪个领域。
16. 作为技术读者，在句子模式下翻译一段包含代码的长句时，我希望系统提示词同样注入当前选中的角色，以便整段译文的措辞口吻和行业用词与我的专业背景一致。
17. 作为技术读者，如果我在卡片内快速连续点击切换不同角色，我希望系统自动中止（abort）尚未完成的前序请求，以便界面始终显示最后一次点击的准确结果，防止异步乱序覆盖。
18. 作为技术读者，如果我输入的角色 Prompt 偏离常规导致模型返回格式不符合词典规范，我希望系统能自动降级为文本展示而不白屏报错，以便我的阅读体验不受阻断。

## Implementation Decisions / 实施决策

### 1. 架构与数据契约（Data Model & Storage）

- 自定义角色属于用户个性化业务数据，存储于本地 SQLite（由 Drizzle ORM 管理），新增独立表 `personas`（与 `vocab`、`glossaries` 平级）：

```ts
export interface Persona {
  id: string; // 主键 UUID
  name: string; // 角色简称 (≤12 字符，供卡片胶囊展示)
  prompt: string; // 角色背景设定 (≤300 字符，注入 Prompt)
  isSystem: boolean; // 是否为系统内置保底角色 (系统角色禁止删除)
  isDefault: boolean; // 是否为全局默认角色 (唯一性约束)
  sortOrder: number; // 卡片标签排序权重
  createdAt: string; // ISO 8601 时间戳
  updatedAt: string; // ISO 8601 时间戳
}
```

- 系统初始化时注入默认保底记录：`{ id: "sys-default", name: "通用技术", prompt: "精通计算机科学与主流软硬件开发的技术专家", isSystem: true, isDefault: true, sortOrder: 0 }`。

### 2. IPC 传输契约扩展

- 通信遵循 `@app/shared` 规范，在 `ipc-channels.ts` 与 `ElectronApi` 中扩充领域通道：
  - `personas:list`: 获取全部角色列表
  - `personas:save`: 新增或更新角色（入参做 Zod Schema 校验：`name` ≤12 字符，`prompt` ≤300 字符）
  - `personas:delete`: 删除指定角色（若 `isSystem === true` 抛出 `AppError.InvalidOperation`）
  - `personas:setDefault`: 切换默认角色
- 在现有的翻译请求契约中，请求参数追加可选 `personaId?: string`。主进程处理时若未指定或 ID 不存在，自动回退到当前全局默认角色的设定。

### 3. 提示词组装与无语境适配

- **单词模式 (`word-v1`)**：
  - 将原系统提示词首句由固定文本 `You are Snapword's English-to-Simplified-Chinese dictionary engine for technical readers.` 动态替换为：
    > `You are Snapword's English-to-Simplified-Chinese dictionary engine. Your persona: ${persona.prompt}`
  - 保留所有后续规则（JSON 输出要求、`word`、`phonetic_us`、`context_sense`、`context_snippet`、`senses` 1~5 条且例句必填）完全不变。
- **“无语境”兜底逻辑**：
  - 当 UIA 上下文为空时，用户模板追加：
    > `Context is unavailable. Infer senses and prioritize definitions based on your persona.`
  - 渲染层接收到结果且上下文为空时，首条义项标签展示为「已按【${persona.name}】推断」。
- **句子模式 (`sentence-v1`)**：
  - 系统提示词同步注入角色：`Translate only the text between the input delimiters into natural, accurate Simplified Chinese as a ${persona.prompt}.`。

### 4. 界面与自适应交互（Card & Settings UI）

- **主窗口「设置」模块**：新增独立设置卡片，提供清晰的列表展现、表单弹窗以及默认角色切换单选框。
- **翻译卡片 Header 交互**：
  - 角色切换控件紧贴模式标签右侧，最大高度对齐 Header；
  - 激活角色总数 ≤ 3 时：直接平铺为 Pill 标签，点击直切；
  - 激活角色总数 > 3 时：平铺当前生效角色与第 2 常用角色，第三项渲染为 `更多 ▾` 下拉菜单；
  - **展示会话内存缓存**：卡片内部维护 `Map<personaId, TranslationResult>`。切换角色时，若命中缓存则瞬时更新 DOM；未命中则带 `AbortController` 发送 IPC 请求，同时旧请求被中止；
  - **会话历史写入策略**：关闭卡片时，将最终呈现的翻译结果及其所属 `personaName` 记录存入主进程 20 条会话历史。

## Testing Decisions / 测试决策

遵循最高测试接缝（Highest Possible Seam）原则，仅对外部可见行为进行黑盒校验：

### 1. 渲染层组件与交互接缝（UI Seam）

- **`SettingsPersonasCard`**：
  - 验证角色列表渲染、表单输入合法性校验（空值、超长拦截）；
  - 验证系统内置角色的「删除」按钮置灰或隐藏；
  - 验证切换「默认角色」时单选互斥正确生效。
- **`CardPersonaSelector` & `TranslateCard`**：
  - 验证当角色数量为 2 个和 5 个时，卡片顶部 DOM 分别渲染为全平铺与下拉菜单形态；
  - 验证点击不同角色标签触发翻译请求，且附带正确的 `personaId`；
  - 验证快速连击角色时，先前的网络请求被正确 `abort`；
  - 验证切回历史已查角色时，不产生二次网络调用（命中会话内缓存）。

### 2. 主进程业务与契约接缝（Service & IPC Seam）

- **`personas.service.ts`**：
  - 验证 SQLite 持久化正常，增删改查逻辑完整；
  - 验证防护逻辑：拒绝删除 `isSystem: true` 的系统角色；
  - 验证单默认逻辑：设置新默认角色时，原子化取消旧默认角色。
- **`translate.service.ts` 提示词拼装测试**：
  - 验证不同角色传入时，生成的 System Prompt 正确插桩角色设定；
  - 验证无论传入何种角色，底层的 JSON Schema 约束与分隔符规则均未被篡改破坏；
  - 验证上下文为空时，注入无语境提示。

## Out of Scope / 范围外事项

1. **社区/云端角色市场**：MVP 仅支持本地 SQLite 存储，不包含角色在线分享、导入导出市场或云端同步。
2. **底层格式自定义**：禁止用户自定义影响输出结构的提示词（如修改 JSON 字段、要求返回 Markdown 格式等），角色 Prompt 仅限于行业领域与专业视角描述。
3. **独立快捷键绑定**：不为各个角色单独分配独立全局热键（如 Alt+1/Alt+2 切换角色）。
4. **角色多语言自动翻译**：角色名称与 Prompt 由用户直接输入，系统不做自动多语言转译。

## Further Notes / 补充说明

- 本规格书完全符合当前 Snapword 三窗口模型约束，未新增第四个常驻窗口，未破坏卡片 420px 宽度及不夺焦核心约束。
- 契约先行原则：此特性落地时，需先行在 `packages/shared/` 补充相关 Schema 与 IPC Channel 声明，并执行迁移脚本更新数据库。
