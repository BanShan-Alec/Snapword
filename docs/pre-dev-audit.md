# Snapword · 开发前文档完备性与信息对齐审计 v1.0

> **版本说明（2026-11-02）**：本审计基于 v1.1.1 的“气泡 + 侧边栏”交互。该交互已被 [PRD-v2.md](PRD-v2.md) 与 [interaction-spec-v2.md](interaction-spec-v2.md) 的三窗口模型取代；本文件保留为历史审计记录，其中与界面交互相关的条目不再作为当前决策依据。
>
> 审计对象：`docs/PRD.md`（v1.1）、`docs/interaction-spec.md`（v1.0）、`README.md`
> 审计日期：2026-10-19
> 审计视角：如果把这三份文档交给一个没参与讨论的开发（或三个月后的你自己），能不能直接开工而不需要再问任何问题？

---

## 0. 审计结论

**产品层已经够了，契约层还不够。**

PRD 说清了「做什么、为什么、什么不做」，交互规格说清了「主链路上每毫秒发生什么」。这两层达到可直接开工的水准。真正缺的是第三层——**接口与数据契约**：进程之间怎么说话、数据库长什么样、模型返回的字段够不够用、什么算通过。

| 维度 | 数量 | 说明 |
|---|---|---|
| 文档间明确冲突 | **22 项** | 其中 5 项属 P0，不裁决会直接返工 |
| 缺失文档 | **12 份** | 4 份阻塞开工，4 份开发前应有，4 份上线前补齐 |
| 有需求但无交互定义的页面 | **4 个** | 生词本、最近、诊断、术语表 |
| 有指标但无法测量的验收项 | **3 项** | 气泡 120ms、对比度 4.5:1、语境义准确率 85% |

**一句话风险**：PRD 的 53 条需求里有 12 条依赖「模型返回什么」和「数据库怎么存」，而这两件事的契约目前只有半页纸。这是最可能在第二周返工的地方。

## 2. 信息未对齐（22 项）

### 2.1 P0 — 不裁决就会返工（5 项）

| 编号 | 冲突点 | 现状 A | 现状 B | 建议裁决 |
|---|---|---|---|---|
| A-01 | **单词输出缺字段** | FR-20 的 JSON schema 只有 `word / phonetic_us / phonetic_uk / context_sense / senses` | FR-26 要求「附原句片段」、FR-33 收藏要存 `context_snippet`、10.1 数据实体也有该字段 | **schema 补 `context_snippet`（string\|null，≤50 字符）**。否则前端无数据可展示，收藏也存不进去。这是三处需求同时指向一个不存在的字段 |
| A-02 | **「OpenAI 兼容」没有兼容基线** | FR-17/19/20 只写「仅支持 OpenAI 兼容接口」，依赖流式、JSON 输出、usage 返回 | 各厂商兼容程度不同：`max_tokens` vs `max_completion_tokens`、`response_format` 是否支持、`stream` 分块格式、`usage` 字段名 | **定基线**：只依赖 `chat/completions` + `stream` + 纯 prompt 约束 JSON（不强制 `response_format`）。`usage` 缺失时降级为不计费。这条不写清，联调期必然被 DeepSeek / Ollama / 中转服务逐一打脸 |
| A-03 | **生词本唯一键未定义** | FR-33 要求「重复收藏同一词条 → 提示已存在」 | 未定义「同一词条」的判定：按 `word`？按 `word + source_url`？大小写、词形变化（`thread` / `threads`）算不算同一个？ | **按 `word` 归一化后（小写 + trim）唯一**，`source_url` 只作为「最近一次来源」覆盖写入。理由：用户心智里生词本按词去重，不按页面 |
| A-04 | **术语表存哪没定** | 10.1 写「Term：SQLite **或** config」 | FR-44 配置项里术语表归在「术语」组，暗示进 config | **进 SQLite**。理由：术语表要支持导入导出、逐条生效、量级可能上百条，塞进 config.json 会让文件损坏风险叠加（FR-45 已有配置损坏处理逻辑，不该让它承担两份数据） |
| A-05 | **senses 条数谁截断** | FR-20 schema 的 `senses` 是数组，无条数限制 | FR-26 说「最多显示 5 条」 | **提示词要求模型最多返回 5 条，前端不截断只兜底**。理由：让模型只产 5 条能省 token；若模型返回更多才截断。这条不定，token 成本和展示逻辑都会漂 |

### 3.1 阻塞开工（4 份）

| 文档 | 为什么阻塞 | 最小内容 |

## 4. 规格空洞：有需求，但没写怎么用

这四块不是「缺文档」，是**文档里那一段没写**，开发到这里只能自己发挥。

| 缺口 | 现状 | 影响 |
|---|---|---|
| **生词本页面** | FR-33/36/37/38 共 4 条需求（列表、搜索、删除、批量删、清空、导出 CSV/JSON、隐私入口），附录 A 原型只画了气泡/侧边栏/空态，交互规格第五章只写了首启和设置 | 一个完整页面（含空态、批量选择、导出对话框、二次确认）全部空白，是本项目**最大的单点空白** |
| **「最近」入口** | FR-34 要求侧边栏底部有入口，交互规格 UX-4 仍「待定」（抽屉/小窗/浮层） | 待定项没有默认值，开发会先做一个然后返工 |
| **诊断页** | FR-46 只列了 8 个检查项和输出内容，没有页面结构、没有「复制为文本」的按钮位置、没有失败项的高亮规则 | 直接影响 RK-01 的止血能力 |
| **术语表管理** | 交互 5.2 仅一行「表格内联编辑；每行保存即生效」 | 导入导出、匹配方式（完全/包含/正则）的输入控件、正则非法时的校验，全无 |

另有 4 项规格缺口：

| 项 | 说明 |
|---|---|
| **视觉规范** | 非功能要求「对比度 ≥ 4.5:1」，但全文没有一个色值。**这条要求目前不可验收** |
| **i18n 布局规则** | S-14/FR-49 要求双语，但交互 2.5 的文案规范只有中文示例。英文字符串普遍比中文长 30~50%，96px 气泡、320px 侧边栏下限、按钮文字都会溢出。**需要一条「文案长度上限」规则** |
| **代理与网络** | FR-44 配置项里没有代理设置，非功能只说「除 Base URL 外无外连」。国内直连官方 API 大概率失败，E-04 只给「检查代理」，但产品不提供配置入口——只能靠系统代理。这个取向要写明，否则是高频 issue |
| **待实测项（D-1/2/6/7）** | Q-1 已于 2026-11-02 完成（见 [research/uia-validation-2026-11.md](research/uia-validation-2026-11.md)）；剩余 D-1 成功率统计、Q-6、Q-2（全屏置顶，建议开发第 2 周前验完，决定 FR-09）、Q-7 |

| 不用做 | 理由 |
|---|---|
| ADR 决策记录 | README 那张 10 条决策表已经承担了 80% 的作用，把「为什么不选 B」补进去就够，不需要独立体系 |
| 完整威胁模型 | 单人开源工具、无服务端、无账号，PRD 11.2 那张风险-措施表已经覆盖实际攻击面。等到有人提安全 issue 再补 |
| WBS / 甘特图 | 单人项目的排期价值低，一张「第一批/第二批/第三批」的顺序表足够 |
| CONTRIBUTING / CODE_OF_CONDUCT | 首个外部 PR 出现前都没用 |

---

## 7. 三条要记住的判断

1. **P0 的 5 项全是「单词链路」的**——不是巧合。单词模式是唯一「模型输出直接决定界面结构」的地方，句子模式只是纯文本，容错高得多。风险集中在这里，加固也应该在这里。
2. **两份文档的边界上最容易漏**：PRD 管「要什么」，交互管「怎么变」，中间那层「数据长什么样」两边都以为是对方的事。A-01（缺 `context_snippet`）就是典型——三处需求引用同一字段，而这个字段从未被定义。
3. **「必须是 Should」这类矛盾不是笔误，是决策悬空**。A-08 / A-13 / A-14 三项都属于「当时没拍板，两边各写了一个答案」。这类问题不改文档就不会暴露，一直到开发时才发现要选一个。
